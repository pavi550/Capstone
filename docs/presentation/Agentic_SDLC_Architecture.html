How an AI team turns one Jira ticket into live code

This page explains the Agentic SDLC architecture by following a single real ticket from the moment it is written to the moment it is deployed. Each chapter shows who acts, what they produce, where a human steps in, and what happens when something goes wrong.

As you scroll, the architecture diagram on the right lights up the parts of the system that are working in that chapter.

Chapter 1 · The request

A product owner writes a ticket

Our story starts with NETOPS-101. The network operations team wants the telemetry service to raise an alarm when a network link runs hot, and to clear it only when traffic has clearly dropped, so the alarm does not flap. The details live in a Confluence functional spec.

The system gathers everything the ticket depends on: the Jira item, the linked documents (Markdown, Confluence HTML export, Word or JSON), the team's coding standards, and the path to the repository that must change.

Human gate 1

A person confirms: "Yes, these are the right requirement documents." Nothing runs without this.

If it goes wrong

No documents found: the system asks for a path. Still nothing, or the human rejects them: the run stops as blocked.

Parts involved: Jira, Confluence documents, coding standards, Git repository, human reviewer
Chapter 2 · The memory

The system reads everything and builds a knowledge base

An AI writes good code only when it understands the request and the existing code. So before anyone codes, the Knowledge Base Agent reads the documents and pulls out each requirement with its acceptance criteria.

In parallel, the RAG pipeline cuts the documents and source code into small chunks, turns each chunk into a vector (embedding) and stores it in ChromaDB. Later, when the Coding Agent asks "how is link utilisation calculated?", it gets back only the few chunks that answer that question, such as telemetry/collector.py.

Behind the scenes: RequirementKnowledgeBase.skills.md

REQ-001 Utilisation alarm 3 acceptance criteria REQ-002 Alarm clear (hysteresis) 2 acceptance criteria status: pending · source: link_utilisation_alarms.md

Human gate 2

A person approves the extracted requirements. This is the cheapest moment to catch a misunderstanding.

Produces

RequirementKnowledgeBase.skills.mdknowledge_base.jsonvectors in ChromaDB
Parts involved: Knowledge Base Agent, chunking and embedding, ChromaDB, LLM
Chapter 3 · The manager

The Orchestrator breaks the work into tasks

The Orchestrator Agent is the project manager of the AI team. It is built as a LangGraph state graph: every step is a node, and the graph remembers where NETOPS-101 is at all times.

Its Task Planner turns each requirement into concrete tasks and records them. The Orchestrator then checks the most basic thing: is there a repository to work in? The Coding Agent is only called when there is.

Behind the scenes: TaskPlanner.md

T-REQ-001-1 Add utilisation_pct(traffic_bps, capacity_bps) to the alarms module T-REQ-001-2 Raise a MAJOR alarm at 85.0% or more T-REQ-002-1 Clear an active alarm only below 80.0% (hysteresis) each task is linked to its requirement and acceptance criteria

If it goes wrong

No repository, or it cannot be read: the system writes CONCERN.md explaining why and stops with status blocked (exit code 2) instead of guessing.

Parts involved: Orchestrator Agent (LangGraph), Task Planner, repository check
Chapter 4 · The rules

Guardrails are set before any code is touched

Before letting AI agents write into a real codebase, the Orchestrator puts up fences.

  • Own branch: work happens on agentic/<run-id>. The branches main, master, develop and release/* are protected and never committed to.
  • Allowed paths only: .git, .env, keys and secret files can never be written.
  • Approved tools only: MCP integrations such as Gerrit must be on the approved list and confirmed by a human.
  • Baseline: the existing tests run once, so later failures can be blamed correctly.

Human gate 3

"Allow the orchestrator to use Gerrit?" If the answer is no, the run stops.

Parts involved: Guardrails, Git repository, MCP tool approval, audit log
Chapter 5 · The builders

Two agents work side by side: one codes, one tests

For REQ-001, the Coding Agent and the Test Agent start at the same time.

Coding Agent retrieves context from the knowledge base, follows the coding standards and asks the LLM to write the code. Its SWE bots find the right files, edit them, build, and fix their own errors.

Test Agent turns each acceptance criterion into a test. Because it works from the requirement, not from the code, its tests check what the business asked for.

Behind the scenes: what each agent writes

# telemetry/alarms.py (Coding Agent) def utilisation_alarm(util_pct): return "MAJOR" if util_pct >= 85.0 else None # tests/test_alarms.py (Test Agent) assert utilisation_alarm(85.0) == "MAJOR" assert utilisation_alarm(84.9) is None assert utilisation_alarm(90.0) == "MAJOR"

Checked on every write

Each file path is validated against the guardrails, the content is scanned for secrets, and the Test Agent may only write test files. A violation sends the work straight back to the agent.

Parts involved: Coding Agent + SWE bots, Test Agent, LLM, knowledge base, guardrails
Chapter 6 · The twist

A test fails, and the system works out who is wrong

The first run fails: one test expected utilisation_alarm(85.0) == "MAJOR", but an early draft of the code used util_pct > 85.0 instead of >=.

Instead of blindly retrying, the Triage Agent reads the failure and decides what caused it:

  • Code is wrong: the Coding Agent gets the failure and fixes the code. (This is our case.)
  • Test is wrong: only the Test Agent reruns.
  • Requirement is wrong: a human is asked to correct it, the knowledge base is rewritten, and both agents rerun.

Every pass also goes through the lint gate and a quality score out of 100: failing tests cost 40 points, lint issues 10, and long functions, deep nesting or duplicated lines cost a few points each.

Behind the scenes: run log

==> [REQ-001] tests FAILED; quality score 60/100 (tests failing) ==> [REQ-001] failure triage -> code: threshold boundary 85.0% excluded ==> [REQ-001] tests passed; quality score 100/100

Safety limit

At most 3 fix attempts per requirement. After that the requirement is marked failed and nothing is integrated or deployed.

Parts involved: test runner, quality evaluator, Triage Agent, Coding / Test Agent, human (for requirement fixes)
Chapter 7 · The inspectors

Two reviewers inspect the change, and a vote removes the noise

Passing tests is not enough. The Review Agent checks the change the way a senior engineer would.

Step 1, context engine: it takes the diff plus a full code index and collects the code that matters: the changed functions, who calls them, what they import, and the related tests.

Step 2, two reviewers in parallel: the Security reviewer looks for secrets, injection, unsafe deserialization, weak crypto and similar holes. The Pattern reviewer looks for broad excepts, debug prints, TODOs, deep nesting and very long functions. Each has a rule-based checker and an LLM checker.

Step 3, ensemble vote: findings about the same issue are grouped. Each reviewer's vote is its weight times its confidence, and the votes are combined. A finding is kept only if the combined score reaches 0.5.

Behind the scenes: the vote for NETOPS-101

Finding A yaml.load() on the alarm-threshold config (SEC-DESERIALIZE, high) security_rules 1.0 x 0.75 = 0.75 security_llm 0.8 x 0.70 = 0.56 combined = 1 - (1-0.75)(1-0.56) = 0.89 KEPT, blocking Finding B print() left in alarms.py (PAT-DEBUG-PRINT, low) pattern_rules 0.9 x 0.40 = 0.36 combined = 0.36 DROPPED as noise

Finding A is high severity, so the review fails and the code goes back for refinement (switch to yaml.safe_load). On the second pass the review passes. A review also fails if the quality score is below 60. At most 2 review rounds are allowed.

Produces

review-REQ-001.json with kept and dropped findings, noise reduction, and each reviewer's precision, recall and F1 against the consensus.
Parts involved: context engine, security reviewer, pattern reviewer, ensemble, LLM
Chapter 8 · The next requirement

The same loop runs again for REQ-002

REQ-001 is now implemented, and the knowledge base records it. The Orchestrator moves to REQ-002 Alarm clear (hysteresis) and runs the same cycle: code and tests in parallel, run, triage if needed, review.

Integration only starts when every requirement of the ticket is implemented, tested and reviewed. If any one fails, the run stops before touching Git, so half-finished work never reaches reviewers or production.

Behind the scenes

==> [REQ-001] implemented in 2 iteration(s) ==> [REQ-002] start: Alarm clear (hysteresis) ==> [REQ-002] tests passed; review passed: 0 findings kept ==> [requirements] all 2 requirements implemented, tested and reviewed
Parts involved: Orchestrator, Coding Agent, Test Agent, test runner, Review Agent
Chapter 9 · The hand-off

The change goes to Gerrit and CI

The Orchestrator makes one commit on the work branch containing only the files the agents wrote plus the documentation, never build output.

Behind the scenes: commit message

feat: implement REQ-001, REQ-002 - REQ-001 Utilisation alarm: tests pass, review passed, quality 100 - REQ-002 Alarm clear (hysteresis): tests pass, review passed, quality 100

Human gate 4

"Push agentic/<run-id> to Gerrit for review?" Once approved, it is pushed to refs/for/main where a human engineer reviews the patch set.

Then the CI/CD pipeline builds everything and runs the full regression suite, to make sure the new feature has not broken something else.

If it goes wrong

A regression failure is sent to the Coding Agent as a "fix CI regression" task. At most 2 CI attempts, then the run is marked failed.

Parts involved: Git, Gerrit (via approved MCP), CI/CD pipeline, human reviewer
Chapter 10 · The launch

Documented, deployed, and closed

With CI green, the system writes the Definition of Done checklist and a traceability matrix that links every requirement to its code, tests and review.

Behind the scenes: traceability.md

REQ-001 -> telemetry/alarms.py -> tests/test_alarms.py -> review passed REQ-002 -> telemetry/alarms.py -> tests/test_alarms.py -> review passed

Deployment is promoted one environment at a time: Dev → QA → Staging → Production.

Human gate 5

Each environment needs its own approval. Saying no stops the promotion there; a failed deployment marks the run failed.

Finally, NETOPS-101 is closed in Jira with a link to the commit. Network operators now get a MAJOR alarm when a link reaches 85% utilisation, and it clears only below 80%, so the alarm no longer flaps.

Parts involved: documentation, deployment pipeline, Jira, audit log, human approver

The architecture in one view

What you just followed, summarised: the moving parts, the loops that keep quality high, and what every run leaves behind.

The AI team

  • Orchestrator: plans and routes the work
  • Knowledge Base Agent: extracts requirements
  • Coding Agent: writes and fixes code
  • Test Agent: writes tests from acceptance criteria
  • Triage Agent: decides what caused a failure
  • Review Agent: security, pattern and ensemble review

Three loops, each with a limit

  • Fix loop: failed tests or lint go back to code, tests or requirement (max 3)
  • Review loop: blocking findings or quality below 60 go back to code (max 2)
  • CI loop: regression failures go back to code (max 2)

The limits mean the system never runs forever; it stops and reports instead.

Where humans stay in control

  • Approve the requirement documents
  • Approve the knowledge base
  • Approve tool access (Gerrit MCP)
  • Correct a wrong requirement
  • Approve the Gerrit push and review the patch
  • Approve each deployment

What every run leaves behind (in .agentic_sdlc/)

RequirementKnowledgeBase.skills.mdThe requirements and acceptance criteria the agents worked from, with their status
TaskPlanner.mdThe tasks each requirement was broken into
review-<REQ>.jsonKept and dropped review findings, noise reduction, reviewer precision / recall / F1
DoD.md · traceability.mdDefinition of Done checklist and the requirement → code → test → review links
runs/<id>/report.mdA readable summary of every stage of the run
runs/<id>/events.jsonlThe audit trail: every stage, file write, guardrail denial and human approval, with timestamps
CONCERN.mdOnly when the run is blocked: why it stopped (for example, no repository)
In one sentence: a Jira ticket comes in, AI agents understand it, plan it, build and test it in parallel, diagnose their own failures, review it with a noise-filtering vote, and deliver it through Gerrit and CI, while humans approve every step that matters and every action is recorded.
