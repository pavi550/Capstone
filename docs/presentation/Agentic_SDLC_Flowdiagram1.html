Security checks explained (7a. Security Code Review)

These checks run on the generated code before it is merged. They look for security holes, not functional bugs.

SAST
Static Application Security Testing
Reads the source code without running it and flags insecure patterns, e.g. SQL built from user input (SQL injection), shell commands built from input, weak encryption. Tools: SonarQube, Semgrep, Bandit, Checkmarx.
Secrets scan
Finds passwords, API keys, tokens or private keys hard-coded in code or config files – important because AI-generated code can include credentials. Tools: detect-secrets, Gitleaks, TruffleHog.
Dependency / CVE scan
also called SCA – Software Composition Analysis
A CVE (Common Vulnerabilities and Exposures) is a publicly listed, numbered flaw in a specific software version, e.g. CVE-2021-44228 “Log4Shell” in Log4j. The scan checks every third-party library version against the CVE database and reports the fixed version. Tools: pip-audit, npm audit, OWASP Dependency-Check, Snyk, Trivy.
OWASP checks
Open Worldwide Application Security Project
Reviews the application against the OWASP Top 10 – the most common web risks such as broken access control, injection, cryptographic failures, security misconfiguration and vulnerable components. Because this flow uses LLM agents, the OWASP Top 10 for LLM Applications (prompt injection, excessive agency, etc.) also applies.
Related (after deployment)
DAST (Dynamic Application Security Testing) attacks the running app from outside; penetration testing is a manual simulated attack. These run against deployed environments, not in 7a.
